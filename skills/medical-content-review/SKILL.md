# 医学監修（医学的内容レビュー）

## このスキルが解く問題

医療参照アプリの誤りは「タイプミス」の顔をして入ってこない。実際に見つかるのは、
**原典そのものが内部で矛盾していて、実装者がどちらか一方を無自覚に選んだ**という形が圧倒的に多い。

原典の概要表と詳細章で数値が食い違っていても、どちらも「原典に忠実」なので、
原典との突合（差分チェック）では絶対に捕まらない。捕まえるには、
原典の**中**を相互に突き合わせ、さらに外部のガイドラインを当てる必要がある。

この非対称性が、以下の3軸を分けて回す理由である。軸を混ぜると、
機械的に潰せる作業（軸2）に時間を吸われて、本当に危険な軸3に到達できない。

## 3つの監査軸

| 軸 | 問い | 主な手段 | 典型的な所要 |
| --- | --- | --- | --- |
| 軸1 日本語 | 読み違えを誘う表現はないか | 機械スキャン＋通読 | 小 |
| 軸2 原典一致 | 原典の記載を正しく写しているか | スクリプトで全件照合 | 小（自動化できる） |
| 軸3 医学的妥当性 | 原典の内容自体が現在の医学で妥当か | 一次資料の当たり込み | **大（ここに時間を使う）** |

軸2 は必ず**スクリプトで全件**回す。人間が目視で全件見るのは不可能だし、
サンプリングでは「1件だけ違う」を落とす。逆に軸3 は自動化できないので、
軸2 を自動化して浮いた時間を全部こちらに回す。

## エビデンスの階層

採否は「誰が書いたか」ではなく「どの強さの根拠か」で決める。

| 階層 | 資料 | 扱い |
| --- | --- | --- |
| A | 直近10年の査読論文（国内・英語）、そのメタ解析・システマティックレビュー | 最優先。これに反する記載は修正対象 |
| A | 学会・公的機関の診療ガイドライン（最新版） | 最優先。版が古ければ改訂の有無を必ず確認 |
| B | 電子添文（添付文書）／PMDA | 保険診療・法的な上限の根拠。**臨床的最適とは限らない**ので A と衝突したら両論併記 |
| C | 標準的な教科書、総説 | A・B が無いときの裏付け |
| D | 10〜20年前の論文 | 参考程度。単独では修正根拠にしない |
| E | 20年以上前の論文、伝聞、院内の口伝 | 根拠として扱わない。「エビデンス未確認」に分類する |

**B（添付文書）と A（ガイドライン）はしばしば食い違う。** 添付文書は承認当時の
臨床試験に縛られ、改訂が遅れる。日本の添付文書上限を超える用量が国際的な標準治療、
ということは普通に起きる（例：ダプトマイシンの左心系心内膜炎）。
この場合「どちらかが誤り」ではなく、**両方を出典付きで併記し、保険上の制約を明示する**のが正しい。

**根拠が見つからないものは、消さずに「エビデンス未確認」として明示的に列挙する。**
黙って残すと次のレビューで同じ調査を繰り返すことになり、黙って消すと院内合意を壊す。
未確認リストは次回レビューの入口になるので、レポートに必ず節を立てる。

詳しい判断基準と、資料が衝突したときの書き分けは `references/evidence-grading.md` を読む。

## 手順

### Phase 0. 原典をテキスト化する

照合対象の原典（PDF）を、ページ番号タグ付きのテキストに落とす。
以降のすべてのスクリプトがこの形式を前提にする。

```bash
python skills/medical-content-review/scripts/extract_pdf_text.py <input.pdf> <output.txt> --tag manual
```

出力は `===== [manual p.10] =====` という行で各ページが区切られる。

**引用ページ番号が印刷ページ番号かPDF物理ページ番号かを最初に確認する。**
ここがずれていると以降の照合が全滅し、しかも「全件不一致」という
一見もっともらしい結果が出るので気づきにくい。既知の数値を1つ選び、
それが期待するページに載っているかを必ず手で確かめてから先へ進む。

### Phase 1. 軸2 — 原典との一致を全件照合する

```bash
node skills/medical-content-review/scripts/check-source-fidelity.mjs \
  --pages <extracted.txt> --data <data.json> --config <fields.json>
```

用量文字列から「数値＋単位」トークンを抽出し、引用ページに実在するかを見る。

**このスクリプトの出力は「検出」であって「誤り」ではない。** 必ず1件ずつ原典を開いて確認する。
実際に出る偽陽性は次の形が多い（いずれも原典側の書き方の問題で、データは正しい）：

- 数値と単位の間に語が挟まる — `20〜40 mg（力価）/kg` は `20-40mg/kg` と一致しない
- 単位が数値の途中に入る — `3%〜10%` は `3-10%` と一致しない
- 漢数字・割合表現 — 原典 `約9割` に対しデータ `約90%`
- 意図的な逸脱 — 前回のレビューで原典の誤りを修正した箇所

最後の「意図的な逸脱」は**残っていなければおかしい**。過去のレビュー文書と突き合わせ、
消えていたら回帰（次のデータ更新で原典の誤りが再混入した）を疑う。

### Phase 2. 軸3-a — 原典の内部不整合を洗う（最重要）

**ここが最も収量が高い。** 原典は普通、同じ項目を複数箇所に書く。

- 巻頭の一覧表 ↔ 各論の詳細章
- 成人編 ↔ 小児編
- 通常用量の表 ↔ 腎機能別用量の表 ↔ 透析・CHDF の表

```bash
node skills/medical-content-review/scripts/check-internal-consistency.mjs \
  --pages <extracted.txt> --terms <terms.json>
```

同じ薬剤名・項目名が出る全ページから数値を集め、ページ間で食い違う組を出す。
これも「検出」なので、1件ずつ原典を読んで**本当に同じ項目の話か**を確かめる。

不整合が見つかったら、次の3つを必ずセットで書く。

1. どちらが正しいか（外部の一次資料で決める）
2. 実装がどちらを採用しているか
3. 採用側が誤っている場合、それが**過小投与か過量投与か**

過小投与は「安全側の間違い」に見えるが、抗菌薬では治療失敗と耐性化を招くので
過量と同じ重さで扱う。目標血中濃度の下限が下がっている、といった形で現れる。

### Phase 3. 軸3-b — 一次資料に当たる

Phase 2 で出た不整合と、下のチェックリストで挙がった項目について、
階層 A の資料を実際に読む。要約や二次情報で済ませない。

`references/review-checklist.md` に、2026年時点で特に確認すべき薬剤クラス別の
着眼点（TDM目標値、腎機能別用量、CHDF、小児、適応外）をまとめてある。
**レビュー開始時に必ず読む。** どこを見るべきかの当たりがつく。

ガイドラインPDFは要約させず、必ず全文を落として原文の推奨文を引く。

```bash
python skills/medical-content-review/scripts/extract_pdf_text.py <guideline.pdf> <gl.txt> --tag gl
grep -n "目標トラフ\|推奨する" gl.txt
```

推奨文は「CQ〇．…」の直後にあることが多い。**推奨度（I / II / III など）まで含めて引く。**
推奨度が III-A（専門家の意見）なのに「ガイドラインが推奨」と書くと、
根拠の強さを誤って伝えることになる。

### Phase 4. 修正案を書き、適用範囲を分ける

見つけたものを優先度で仕分ける。

| 優先度 | 意味 |
| --- | --- |
| P0 | 過量投与、投与速度、禁忌判断など患者安全に直接影響する。公開前に修正必須 |
| P1 | 用法・期間・目標値・モニタリング方針の欠落、または現行ガイドラインとの重要な不一致（過小投与を含む） |
| P2 | 表記ゆれ、境界値の曖昧さ、転記ミスを誘発する誤植 |

そのうえで、**自分で直してよいもの**と**施設の承認が要るもの**を必ず分ける。

- **適用してよい**：全国ガイドラインへの適合（TDM目標値など）、表示順、誤字、
  過去のレビューで既に方針が決まっているもの
- **提案にとどめる**：施設が決めた用量表そのものの変更、採用薬、申請ルール、
  アンチバイオグラム。これらは「その施設が決めたこと」であり、
  勝手に変えるとアプリが表示すべき内容（施設の取り決め）から乖離する

判断に迷ったら提案側に倒す。医療者は「アプリに書いてある＝院内で決まったこと」として読む。

## レポートの形

同じ形で書き続けることに意味がある。次のレビューが前回との差分で走れるようになる。

```markdown
# <対象> 医学監修レポート（第N次）

- レビュー日 / 対象原典 / 比較資料（版と参照日を明記）
- 結論（3行以内）

## 1. 監査方法とカバレッジ
   軸ごとに、全件機械照合したのか標本抽出なのかを書く。限界も書く。

## 2. 指摘事項
   各項目に: 所在（ファイル・原典ページ）／現在の記載／問題／
   **根拠（階層と出典URL・推奨度）**／修正案／優先度／適用可否

## 3. エビデンス未確認の項目
   根拠が見つからなかったもの。次回の入口になる。

## 4. 今回適用した修正 / 提案にとどめた修正
```

**根拠のない指摘は書かない。** 「〜が望ましい」だけの指摘は次のレビューで再検証できず、
レポートの信頼性を下げる。出典が引けないなら §3 に置く。

## 落とし穴

- **原典が正しいと仮定しない。** アプリの誤りより原典の誤りのほうが多い。
  そして原典を直さずアプリだけ直すと、次のデータ更新で再混入する。
  原典側の修正文案もレポートに残す。
- **スクリプトの正常終了を成功と読まない。** 正規表現の破損や
  ページ番号のずれで、照合が0件のまま「全件合格」に見えることがある。
  スクリプトには必ず「読み込んだページ数」「照合した件数」を出力させ、
  数が想定どおりかを見る。既知の不一致を1件仕込んで検出できるか試すのが確実。
- **ヒアドキュメントでスクリプトを書かない。** バックスラッシュが1段落ちて
  正規表現が黙って別物になる。ファイルとして書き出す。
- **「調整不要」と「データなし」を混同しない。** 前者は薬物動態上の結論、
  後者は情報の欠落。同じ空欄で表示すると臨床判断を誤らせる。
- **削除は最後の手段。** 根拠が弱い記載は、消すのではなく
  「根拠が限られる」旨を添えて残すほうが安全なことが多い。
  医療者は記載が消えた理由を推測できない。

## 反復

1回で終わらせない。1周ごとに軸3の対象クラスを変えて回す。
`references/review-checklist.md` のクラス一覧に、
レビュー済みの日付を書き込んでいくと、次に見るべき場所が自明になる。
