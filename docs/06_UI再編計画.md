## 0. この再編の要旨

現行UIは **起動直後に「成人／小児」を選ばせる**構造（FR-000）を最優先原則としていた。
これを取りやめ、**原典の章立てに沿った4つの大項目**を入口にする。

| | 現行 | 再編後 |
| --- | --- | --- |
| 入口 | 成人／小児の2択（必須・既定値なし） | 内服薬／注射薬／菌名／周術期 の4択 |
| 成人・小児 | アプリ全体のモード。全画面に波及する | **薬剤レーンの第2階層**。内服薬・注射薬を選んだ後にのみ選ぶ |
| 菌名・周術期 | 成人／小児を選ばないと到達できない | 集団の選択なしで直接到達できる |
| 薬剤の絞り込み | 全74剤を横断検索のみ | 剤形レーンで分割 → 内服はAWaRe分類でも絞れる |
| TDM | 入力が欠けると初回投与量が消え、目標トラフのみが残る（不具合） | 初回投与量と採血タイミングを常に提示。実測値による計算は §3 で検討 |

### なぜ「成人／小児を最初に選ばせる」のをやめるのか

成人・小児で分けること自体は妥当であり、廃止しない。**問題は分ける「位置」である。**

1. **成人／小児が不要な画面まで巻き込んでいる。** 菌名検索・アンチバイオグラムは菌側の情報であり、患者集団に依存しない。周術期予防も原典は体重帯（`weightMin`/`weightMax`）で用量を決めており、成人／小児の区分を用いない。にもかかわらず現行は、これらを見るためにも起動時に集団を選ばされる。
2. **原典の構造と一致しない。** 原典は「注射薬／内服薬／菌／周術期」で章立てされ、成人・小児は各章の中の区分にすぎない。入口で分けると目次構造がずれ、「マニュアルのどこを見ているか」が見えなくなる。
3. **モード切替の副作用が大きい。** 現行は小児用量を見るとアプリ全体のモードが切り替わる（`onSwitchMode`）。閲覧のつもりの操作がグローバル状態を書き換えるため、戻し忘れると以降ずっと誤った集団の用量を見続けることになる。

### 解決: 成人／小児を薬剤レーンの第2階層へ下ろす

集団の選択が**実際に用量を左右する画面でだけ**行われるようにする。

```
内服薬 ─→ [成人] または [小児] ─→ 検索・AWaRe絞り込み ─→ 薬剤詳細
注射薬 ─→ [成人] または [小児] ─→ 検索・系統絞り込み   ─→ 薬剤詳細
菌名   ─────────────────────────→ 菌検索 ─→ アンチバイオグラム   （集団の選択なし）
周術期 ─────────────────────────→ 領域選択 ─→ 推奨薬・体重帯別用量（集団の選択なし）
```

この形は、当初の設計原則が持っていた**「片方の集団の用量しか画面に出さない」という構造的な誤参照防止を維持したまま**、
不要な画面から集団選択を取り除く。版1.0で検討していた「両方を並記する」案は、
同一画面に両集団の用量が出るため取り違えのリスクが上がる。**版2.0ではこれを採らない。**

したがって旧FR-000の安全要件は、適用範囲を薬剤レーンに限定したうえで**そのまま存続**する。

- 選択中の集団は薬剤レーン内の全画面でヘッダーに常時表示し、色分けする（成人＝ブルー系／小児＝グリーン系）。
- 薬剤詳細に表示する用量は**選択中の集団のもののみ**とする。他方は同一画面に並べない。
- 他方の集団を見るときは明示的なリンクを踏ませ、遷移先で切り替わったことを通知する。
  ただし切替の効果は**そのレーン内に限定**し、菌名・周術期には波及させない。
- **小児は体重未入力なら mg/kg 表記のみ**とし、絶対量(mg)を出さない（旧FR-000-5）。
- 原典に小児量の記載がない薬剤は「原典に記載なし」と明示し、推定値を出さない（旧FR-000-6）。

### データ上の裏付け（実地確認済み）

4象限すべてが実用的な件数を持ち、レーン分割が空振りしないことを確認した。

| | 成人 | 小児 |
| --- | --- | --- |
| 内服薬 | 42剤 | 40剤 |
| 注射薬 | 43剤 | 43剤 |

小児のデータを一切持たない薬剤は2剤のみ。小児レーンでは該当薬剤を一覧から除外せず、
「原典に小児の投与量の記載なし」と明示して表示する（存在しないのか記載がないのかを利用者が区別できるようにする）。

## 1. 画面構造（再編後）

```
ホーム
├─ [内服薬] ─→ [成人]/[小児] ─→ 薬名入力欄 ─→ AWaRe絞り込み ─→ 薬剤一覧 ─→ 薬剤詳細 ─→ TDM
├─ [注射薬] ─→ [成人]/[小児] ─→ 薬名入力欄 ─→ 系統絞り込み  ─→ 薬剤一覧 ─→ 薬剤詳細 ─→ TDM
├─ [菌名]   ─→ 菌名入力欄 ─→ 菌一覧 ─→ 菌詳細（アンチバイオグラム）
├─ [周術期] ─→ 領域選択 ─→ 推奨薬・体重帯別の1回量・投与期間
│
├─ 患者条件（ヘッダーから開閉。年齢・性別・体重・身長・Cr・eGFR・腎代替療法）
└─ その他の機能（従属セクション。適応外使用／TDM設計／採用薬一覧／アナフィラキシー／
                 曝露後予防／PCG持続静注／小児体重／適正使用指針・AWaRe／AMR対策）
```

成人／小児の選択はレーンに入るたびに行う。ただし**同一セッション中は直前の選択を初期値として引き継ぎ**、
ヘッダーに常時表示して1タップで切り替えられるようにする（毎回選び直させない）。
菌名・周術期のレーンでは集団のバッジを表示しない（その画面では意味を持たないため）。

### 1.1 大項目4ボタン

原典の章立てに対応する。ホーム最上部に大きめのタイルで配置する。

| ボタン | 対象 | 件数（成人／小児） | 集団選択 | 遷移先 |
| --- | --- | --- | --- | --- |
| 内服薬 | `po` の用量を持つ薬剤 | 42剤／40剤 | **あり** | 内服薬レーン |
| 注射薬 | `iv` / `im` / `inhalation` を持つ薬剤 | 43剤／43剤 | **あり** | 注射薬レーン |
| 菌名 | 菌マスタ全件 | 40件 | なし | 菌検索 |
| 周術期 | 周術期予防抗菌薬 | 15領域 | なし（体重帯で決まる） | 既存の `SurgicalProphylaxis` |

- **内服と注射の両方を持つ薬剤が12剤ある**（レボフロキサシン等）。両レーンに重複して出す。
  ただし各レーンでは**そのレーンの剤形の用量を主表示**とし、他剤形は詳細画面で併記する。
  1剤1ページの原則（設計原則2）は維持し、詳細画面は分けない。
- **どちらのレーンにも出ない薬剤はない**ことを確認済み（`validate-data.mjs` に検査を追加し、
  レーン件数を毎ビルドで出力するようにした）。当初「1剤ある」と見ていたのは吸入薬を
  注射薬レーンに数えていなかった集計の誤りで、`inhalation` は注射薬レーンに含めている。

### 1.2 内服薬レーン

**成人／小児を選んだ後**の画面。利用者指定の順序どおりに配置する。

0. **集団バッジ**（ヘッダー固定）— 「内服薬 ／ 成人」のようにレーンと集団を常時表示し、タップで集団を切り替える。

1. **薬名入力欄**（最上部）
   - プレースホルダ: 「商品名・一般名で検索（例：クラビット、レボフロキサシン、LVFX）」
   - 既存の `searchDrugs` を流用し、**選択中の集団の内服用量を持つ薬剤に限定**して結果を返す
     （成人なら42剤、小児なら40剤）。
   - 入力があればAWaRe絞り込みより検索結果を優先表示する（入力欄が主、分類が副）。

2. **AWaRe分類の簡単な説明**
   - 原典 p.74 の記述を要約して2〜3文で提示する。全文は「適正使用指針・AWaRe」ページへのリンクで送る。
   - 記載必須: 「Accessを増やし、Watch・Reserveを減らすのがWHOの方針」「Access 60%以上が目標」
   - **注記必須**: AWaRe分類は原典では**内服薬に対してのみ**掲載されている（p.74）。注射薬レーンにこの絞り込みは置かない。

3. **分類ボタン → 対象薬剤の絞り込み**

| ボタン | 定義 | 該当数 |
| --- | --- | --- |
| Access | 原典p.74 のAccess欄 | 11剤 |
| Watch | 同 Watch欄 | 10剤 |
| Reserve | 同 Reserve欄 | 1剤（リネゾリド） |
| その他 | 原典のAWaRe表に記載のない内服薬 ＋ Not recommended（アトバコン） | 20剤 |

   - 「その他」20剤のうち19剤の内訳は**抗結核薬3・抗真菌薬7・抗ウイルス薬7・駆虫薬2**で、
     残り1剤が Not recommended のアトバコン。
     WHOのAWaRe分類は抗菌薬（antibacterial）を対象とするため、前者が分類外なのは正常。
     ボタンの補助文言に「AWaRe分類は抗菌薬を対象とするため、抗真菌薬・抗ウイルス薬等は分類対象外です」と添える。
   - ボタンは複数選択可（トグル）。選択解除で全件に戻る。
   - 各ボタンに該当件数を表示する。**件数は選択中の集団で数える**（上表は成人の値。
     小児ではAWaRe分類済みの内服薬が23剤になる）。該当0件の分類はボタンを淡色化し、押せることは維持する。

> **決定（2026-08-27）**: **4ボタン**とする。原典p.74 の `Not recommended`（アトバコン1剤）は
> 当院で使用しないため、独立したボタンは設けず「その他」に含める。
> 原典の情報が失われないよう、薬剤詳細のAWaReバッジには原典どおりの分類を表示する。

### 1.3 注射薬レーン

成人／小児の選択を経る点、および骨格（集団バッジ → 入力欄 → 絞り込み）は内服薬レーンと同じで、
絞り込み軸だけを差し替える。

- 絞り込み: **系統**（`class`。β-ラクタム系／キノロン系／アミノグリコシド系／抗MRSA薬／抗真菌薬 等）
- 併せて表示するバッジ: 「要申請」「要コンサルト」「TDM対象」
- 採用注射薬一覧（規格・薬価・配合変化）への導線をレーン内に置く

### 1.4 菌名レーン / 周術期レーン

既存の `OrganismDetail` / `SurgicalProphylaxis` をそのまま遷移先にする。
入口が大項目ボタンに変わるだけで、中身の変更はしない（今回の再編スコープ外）。

**この2レーンでは成人／小児を選ばせない。** 理由:

- 菌名・アンチバイオグラムは検出菌側の感受性率であり、患者集団に依存しない。
- 周術期予防は原典が体重帯（`ProphylaxisDose.bands` の `weightMin`/`weightMax`）で1回量を決めており、
  成人／小児という区分を用いていない。患者条件の体重が入っていれば該当帯を自動で選ぶ現行動作を維持する。

現行は集団を選ばないとこれらの画面に到達できないが、再編後はホームから直接入れる。

## 2. CCr計算と用量提示（継続・変更なし）

ご指示のとおり**現行の仕組みを維持する**。以下は再確認であり、作り直さない。

- 身長・体重・年齢・性別・Cr から Cockcroft-Gault で CCr を自動計算（`src/lib/calc.ts`）
- 理想体重 IBW = 身長(m)² × 22、補正体重 AdjBW = IBW + 0.4 ×(実体重 − IBW)
- CCr から腎機能区分（>50 / 10–50 / <10 / HD / CHDF）を解決し、薬剤詳細で該当行をハイライト・他行を淡色化
- HD/CHDF は CCr 区分より優先
- 原典に記載のない区分は補完せず「原典に記載なし」と表示

**再編による変更はない。** 版1.0では患者条件パネルに成人／小児を持たせる案だったが、
版2.0では集団を薬剤レーンの第2階層で選ぶため、患者条件パネルは現行のままでよい。

年齢からの成人／小児の自動判定は**行わない**。原典に閾値の記載がなく、
アプリが独自に境界を決めると原典にない判断を持ち込むことになるため、利用者の明示選択のみとする。
ただし年齢と選択中の集団が明らかに矛盾する場合（例: 年齢70歳で小児レーンにいる）は、
用量を書き換えず**注意喚起のみ**を表示する。

## 3. TDM画面の是正と、実測値による投与設計の検討

### 3.1 現状の不具合（コード確認により原因を特定）

「TDM画面に行ったが計算が始まらず、トラフの表示のみだった」というご指摘は**実装上の不具合**であり、
仕様どおりの動作ではない。原因は `Designer.tsx` にある。

#### 不具合A: 入力が欠けると初回投与量が丸ごと消える（バンコマイシン）

```ts
const band = egfr != null ? VCM_TABLE.find((b) => b.test(egfr)) : undefined;
...
{onHd ? ( ... ) : band ? ( ... ) : null}   // ← eGFR未入力かつ非HDでは null
```

患者条件で **eGFR が未入力**（かつ透析でない）と `band` が `undefined` になり、
初回投与量のカードが**何も描画されない**。画面に残るのは目標トラフ値のカードだけになる。
ご覧になった画面はこの状態である。テイコプラニンは初期投与量を無条件に描画しているため、
薬剤によって挙動が違うことになっている。

#### 不具合B: 入力が欠けると腎機能正常時の用量を既定値として出す（アミノグリコシド）

```ts
if (ccr != null && ccr <= 50) { /* 減量・コンサルト */ }
else { /* CCr > 50 の用量を表示 */ }   // ← CCr未入力もここに落ちる
```

CCr が未入力のとき、`else` 側すなわち**腎機能正常時の用量が答えとして表示される**。
行ラベルに「CCr > 50 mL/min」とは書かれるが、「CCrが不明である」ことは用量の隣に示されない。
不具合Aが「何も出ない」なら、こちらは「確度の低い値が確定的に出る」もので、**臨床的にはより危険**である。

#### 不具合C: 欠測時の振る舞いが薬剤ごとにバラバラ

| 薬剤 | 必要な入力が欠けたとき |
| --- | --- |
| バンコマイシン | 初回投与量を**表示しない** |
| テイコプラニン | 常に表示（mg/kg のみ、体重があれば換算） |
| アミノグリコシド | **腎機能正常時の用量を既定値として表示**（欠測の明示なし） |
| ボリコナゾール | 40kg以上の用量を表示（「体重未入力のため」と小さく注記あり） |

同じ「投与設計」を名乗る4画面で作法が4通りある。利用者は薬剤ごとに解釈を変えられない。

### 3.2 是正方針（原典の範囲内。最優先で実施）

ご指示の「まずはTDMが必要な症例に初回投与量・採血のタイミングを分かりやすく表示する」に対応する。
**新しい計算は導入せず、原典に載っている情報を確実に見せることに徹する。**

#### (1) 欠測時の作法を全薬剤で統一する

薬剤詳細の腎機能セクションで既に採用している「**全区分を並べ、該当区分をハイライトし、他を淡色化する**」
パターンをTDM画面にも適用する。

- 患者条件が未入力でも、**原典の投与量表を全区分そのまま表示する**（何も出さない状態を作らない）。
- 該当区分が確定したときだけハイライトし、「この患者は eGFR 45 → この行」と根拠を添える。
- **確定していない区分を既定値として単独表示しない。** 不具合Bを解消する。
- 不足入力は「体重を入力すると mg に換算します」のように**何が得られるか**を書き、
  その場で患者条件パネルを開けるボタンを併置する（現在は文章のみで導線がない）。

#### (2) 初回投与量を画面最上部の主役にする

現在は警告バナー2〜3枚とチェックボックスの下にあり、スクロールしないと届かないことがある。

- 順序を **「初回投与量 → 採血タイミング → 目標値 → 注意事項」** に固定する。
- ローディングドーズがある薬剤（VCM・TEIC）は、初回と維持量を**別行で明示**する。
  現在はローディングが `dose-note` として小さく添えられており、初回投与量として読み取りにくい。

#### (3) 採血タイミングを独立セクションに格上げする

現在は目標値カードの `dose-note`（小さい灰色文字）に埋もれている。原典が持つ以下を構造化して表示する。

| 薬剤 | 初回TDM | 採血時点 | 測定場所 |
| --- | --- | --- | --- |
| バンコマイシン | 5ドーズ目以降（重症例は2–4ドーズ目を考慮） | トラフ=投与直前 | 院内 |
| テイコプラニン | 5ドーズ目以降 | トラフ=投与直前 | 院内 |
| ゲンタマイシン | 2ドーズ目以降 | ピーク=投与終了後30分／トラフ=投与直前 | 院内 |
| アミカシン | 2ドーズ目以降 | 同上 | **院外（外注）** |
| ボリコナゾール | 投与開始2–5日目 | トラフ=投与直前 | **院外（外注・報告日に注意）** |

- 透析患者はいずれも「透析前」に採血する旨を、該当時のみ表示する。
- 外注検査（AMK・VRCZ）は報告までの日数が空くため、**曜日ごとの報告予定**を目立つ位置に出す
  （VRCZの曜日別スケジュールは既にデータにあるが、現在は長い注記文の末尾に埋もれている）。

#### (4) 採血日時の具体化（計算ではなくカレンダー演算）

初回投与日時と投与間隔を入力すると、「**次回採血は ◯月◯日 ◯時（5ドーズ目の投与直前）**」を提示する。
これは薬物動態の推定ではなく、投与間隔とドーズ数の足し算であり、原典の記載
（「5ドーズ目以降でTDMを行う」）を日時に翻訳するだけである。リスクが低く、
病棟での「いつ採血をオーダーすればよいか」という実務の詰まりを直接解消する。

### 3.3 実測値によるTDM投与設計の計算（検討記録・実装しない）

> **決定（2026-08-27）: 実装しない。** 以下は将来の再検討のための記録であり、
> 現在のアプリは段階A（§3.2）までに留まる。

> ご指示: 「マニュアルの記載内容からは逸脱するが、投与時刻、トラフやピークの入力により
> TDMによる治療計画の計算をすることが可能か検討して」

#### 結論

**技術的には可能で、方法論も確立している。ただし、このアプリの性格を変える変更であり、
薬剤部（TDM担当者）の監修と、薬機法上の該当性の確認を経てからでなければ実装すべきでない。**
以下、可否・方法・条件を分けて述べる。

#### (a) 技術的な可否 — 可能

いずれも1-コンパートメントモデルに基づく古典的手法で、特殊なライブラリや外部通信を必要とせず、
現在の完全オフライン構成のまま実装できる。

**アミノグリコシド（Sawchuk-Zaske法）** — ピーク・トラフの2点採血から個別値を求める標準手法。

```
消失速度定数   ke  = ln(Cpeak / Ctrough) / Δt        （Δtは2点の採血間隔）
半減期        t½  = 0.693 / ke
分布容積       Vd  = [D/T × (1 − e^(−ke·T))] / [ke × (Cmax − Cmin·e^(−ke·T))]
新しい投与間隔  τ   = ln(Cpeak目標 / Ctrough目標) / ke + T
新しい1回量     D   = Cpeak目標 × Vd × T × ke × (1 − e^(−ke·τ)) / (1 − e^(−ke·T))
```

**バンコマイシン** — 採血点数により精度が変わる。
- トラフ1点のみ: 定常状態・クリアランス不変を仮定した比例調整（`新用量 = 現用量 × 目標трough / 実測trough`）。簡便だが仮定が強い。
- ピーク＋トラフの2点: 上記と同じ要領で ke・Vd を個別推定し、AUC24 = Dose24 / CL を台形法で算出できる。

**ボリコナゾール** — 非線形（飽和）動態を示すため、上記の線形モデルによる外挿は成り立たない。
**計算対象から除外し、トラフ値の目標域との照合に留める**のが妥当。

#### (b) 臨床的な前提条件 — ここが実装の主要リスク

計算式そのものより、**前提が崩れたときに誤った値が確信を持って表示されること**が危険である。

| 前提 | 崩れる場面 | 対処 |
| --- | --- | --- |
| 定常状態に達している | 初回・2回目の採血、腎機能が変動中 | 何ドーズ目かを必須入力とし、未達なら比例調整を禁止する |
| 投与時刻・採血時刻が正確 | 「だいたい9時」の記録、点滴の遅れ | **時刻は分単位で必須入力**。曖昧なら計算させない |
| 点滴時間が既知 | 記録がない | 点滴時間も必須入力（Sawchuk-Zaske は T を用いる） |
| クリアランスが不変 | AKI進行中、透析導入 | 腎機能の変動があれば警告し、結果を参考値として扱う |
| 線形動態 | VRCZ | VRCZを対象から外す |

したがって実装するなら、**入力が1つでも欠けたら計算しない**（推定で埋めない）ことを絶対要件とする。
これは §3.2(1) で統一する「欠測時は既定値を出さない」方針と同じ考え方である。

さらに、**中間パラメータ（ke, t½, Vd, CL, 推定AUC）を必ず画面に出す**こと。
薬剤師が値の妥当性を検算できなければ、ブラックボックスの提案になってしまう。

#### (c) 位置づけ上の問題 — 最も重要

現在のアプリは、この一線を意識的に引いている。

- 企画書 §7 に「用量計算機能はプログラム医療機器（SaMD）該当性の検討が要る」と明記済み
- 対応として「**院内マニュアルの電子的閲覧支援に留め**、計算は原典に明記された式の実行のみとする」と決めている
- `Designer.tsx` の画面上にも「**原典に記載された表・式のみを実装しています（独自の薬物動態推定は行いません）**」と明示している
- 原典自身、AUCガイドTDMについては学会提供の PAT を使うこととし、「本アプリでは計算しません」としている

実測血中濃度から個別の薬物動態パラメータを推定し、次回の投与量・投与間隔を提案する機能は、
**「マニュアルの閲覧支援」から「投与設計の支援」への質的な変化**である。
画面上の宣言文とも、原典がPATに委ねている方針とも矛盾するため、実装する場合は
これらの記述を改める判断が同時に必要になる。

薬機法上の該当性については、一般に「広く受け入れられた計算式を実行し、医療従事者が結果を検証でき、
最終判断が医師に委ねられるもの」は非該当と整理される例が多い。ただしこれは**私が判断できる事柄ではなく**、
院内の薬事・法務および薬剤部の確認が必要である。本計画では確認すべき事項として挙げるに留める。

#### (d) 推奨する進め方 — 3段階に分け、リスクの低い順に

| 段階 | 内容 | 原典 | リスク | 着手条件 |
| --- | --- | --- | --- | --- |
| **A** | §3.2 の是正（初回投与量・採血タイミングの確実な表示、欠測時の作法統一、採血日時のカレンダー演算） | 範囲内 | 低 | **なし。今回実施する** |
| **B** | 実測値の記録と**判定のみ**。入力されたトラフ／ピークを目標域と照合し「目標域内／下回る／上回る」を表示。用量の提案はしない | ほぼ範囲内 | 中 | 薬剤部の確認 |
| **C** | 個別PKパラメータ推定（ke, t½, Vd, CL）と**用量・間隔の提案**。対象はVCM・GM・AMKのみ、VRCZは除外 | 逸脱 | 高 | 薬剤部（TDM担当者）の監修 ＋ 薬機法該当性の確認 ＋ 免責と画面上の宣言文の改訂 |

段階Bは「アプリが提案する」のではなく「利用者の判断材料を並べる」に留まるため、
臨床的な有用性の相当部分を、位置づけを変えずに得られる。**段階Bまでを次の目標とし、
段階Cはその評価を見てから判断する**ことを提案する。

段階Cに進む場合の追加要件:

- 計算結果には必ず「**参考値。TDM担当薬剤師の確認を得ること**」を併記する
- 中間パラメータを全て表示し、検算可能にする
- 採用した式と出典（Sawchuk-Zaske 等）を画面に明記する。原典ページ併記の原則と揃える
- 入力した血中濃度・時刻も**端末内にのみ保持**し外部送信しない（現行の方針を維持）
- 薬剤部が用意する検証用症例で、手計算との一致をテストとして固定する

## 4. 表組みレイアウトの是正

### 原因（調査済み）

`src/styles.css` で全テーブルに単一クラス `table.abx` が使われており、そこに
`white-space: nowrap` が指定されている（styles.css:341-346）。

```css
table.abx th, table.abx td {
  padding: 7px 9px;
  border-bottom: 1px solid var(--rule-soft);
  text-align: left;
  white-space: nowrap;   /* ← 全9テーブルに一律で効いている */
}
```

これはアンチバイオグラム（数値％・略号のみ・折り返すと読めない）には正しいが、
**日本語の長い説明文を含む表に同じ指定が効いてしまい**、セルが折り返せず横に伸びる。
結果、列幅の配分が崩れ、横スクロールが必要になり読みにくくなっている。

該当箇所（`table.abx` を使う9テーブル）:

| ファイル | 用途 | 適切な型 |
| --- | --- | --- |
| `OrganismDetail.tsx` ×2 | アンチバイオグラム（数値） | 数値表（nowrap 維持） |
| `Reference.tsx:159,192` | 小児体重表・Von Harnack表（数値） | 数値表（nowrap 維持） |
| `Reference.tsx:68` | アナフィラキシー重症度・薬剤（説明文） | **文章表（折り返す）** |
| `Reference.tsx:432` | AWaRe分類（薬剤名・商品名） | **文章表（折り返す）** |
| `SurgicalProphylaxis.tsx:76,156` | 創分類・βラクタムアレルギー代替（説明文） | **文章表（折り返す）** |
| `Formulary.tsx:62` | 採用注射薬一覧（規格・注記・配合変化） | **文章表（折り返す）** |

### 対応方針

1. `table.abx` を **2クラスに分離**する。
   - `table.abx`（数値表）: `white-space: nowrap` 維持、`.scroll` で横スクロール、数値は `tabular-nums` 右寄せ
   - `table.doc`（文章表）: **折り返しあり**、`table-layout: fixed` + 列ごとの `width` 指定、
     `word-break: normal; overflow-wrap: anywhere`、行間を広げる
2. 文章表では**列幅を内容に応じて明示**する。自動配分に任せると、日本語は単語境界がないため
   極端な配分になりやすい。各表で列比率を決め打ちする（例: 創分類表 = 20% / 30% / 50%）。
3. **狭い画面では表をカードに落とす。** 480px未満では `table.doc` を
   「1行 = 1カード、列見出しをラベルとして各値の上に置く」レイアウトへ切り替える。
   横スクロールを利用者に強いない。主戦場がスマートフォンであるため、これは装飾ではなく可読性の要件。
4. `.kv`（定義リスト）の `grid-template-columns: auto 1fr` を見直す。
   `auto` は最長の `dt` に引きずられて左列が過大になる。`minmax(5.5em, max-content) 1fr` に改め、
   狭幅では1列積みへ落とす。

### 作成後の配置チェック（ご指示事項）

**実装後に必ず実施し、結果を報告する。** 目視の主観に頼らず手順化する。

- 本環境の Chromium + Playwright で、**幅 375px / 768px / 1280px** の3種でスクリーンショットを撮る。
- 撮影対象: 大項目4画面 + 表を含む7画面（アンチバイオグラム・採用薬一覧・周術期×2・
  アナフィラキシー・小児体重・AWaRe）
- 判定基準（1つでも該当したら不合格）:
  - `document.body` に横スクロールが発生している（`scrollWidth > clientWidth`）
  - 表のセルが1文字だけで折り返している列がある
  - ある列が表幅の70%以上を占めている
  - テキストが親要素からはみ出している
- スクリーンショットは成果物として提示し、目視でも最終確認する。
