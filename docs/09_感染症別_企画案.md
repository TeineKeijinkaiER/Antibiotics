# 企画案：「感染症別」レーンの新設

- 起案日: 2026-08-28
- 対象: オープニングの大項目に「感染症別」を追加し、感染症ごとの経験的治療から既存の薬剤詳細へ送る
- 原典（予定）: `tekisei_in`（入院）／`tekisei_out`（外来）の2文書 ※**本稿執筆時点で未受領**
- ステータス: **企画案（未承認）**。実装前に §7 の確認事項の回答が必要

## 0. 結論（先に要点）

| 論点 | 結論 |
|---|---|
| 技術的に組み込めるか | **できる。** 既存の画面遷移・データ構造をほぼそのまま流用でき、新規の仕組みはほとんど要らない（§3） |
| 「抗生剤治療の記載→薬剤別解説へ移動」は実現できるか | **できる。** アンチバイオグラムの略号タップ→薬剤詳細と同じ仕組みで実装する。薬剤は**文字列ではなく薬剤IDで持つ**のが肝（§4） |
| 量が多い問題 | **全文は載せない。「表は残す・本文は要約する」**を抽出の原則とし（§2.2）、感染症1件あたり最大7項目に絞る（§2.3）。加えて頻度の高い5疾患から段階的に出す（§6） |
| 最大の懸念 | **技術ではなく規程面。** 現行の要件定義 NFR-012 は「診断・治療方針の提示は行わない」と定めており、本機能はこの線に触れる。実装可否の前に判断が要る（§7-1） |

## 1. 背景と課題

現行アプリの入口は「内服薬／注射薬／菌種別／その他」の4つで、いずれも **薬剤または菌から引く** 構成になっている。
一方、実際の診療では「肺炎の患者が来た」「尿路感染らしい」という **感染症（病名）から引きたい** 場面が多く、
現行アプリではその入口がない。

`tekisei_in` / `tekisei_out` はこの入口を埋める資料だが、**そのまま転記するには量が多すぎる**。
本企画の主眼は「載せる／載せない」の線引きを先に決めることにある。

---

## 2. 編集方針：何を載せ、何を載せないか

### 2.1 原則

> **感染症別レーンは「読み物」ではなく「その場で処方を決めるための索引」とする。**

背景・疫学・病態生理を読ませる場所ではない。ベッドサイドで開いて30秒で答えが出ることを最優先し、
それ以外は原典を見る導線（ページ番号）だけを残す。

### 2.2 抽出の原則：表は残す、本文は要約する

原典から拾う際の優先順位を、**元の書式そのもの**で判断する。

| 原典での書かれ方 | 扱い | 理由 |
|---|---|---|
| **表・一覧にまとめられている記載** | **重要度が高い。構造を保ったまま残す** | 著者が「一覧で引けるべき」と判断した項目であり、そのまま処方判断に使われる |
| 本文（地の文）の記載 | **できるだけ要約する。1〜2行に圧縮** | 背景説明・根拠の記述が多く、ベッドサイドでは読まれない |
| 図・フローチャート | 原則として載せない（ページ参照のみ） | 小画面で判読できず、要約すると意味が変わる危険がある |

補足：

- 表を残す＝**画像として貼るのではなく、表の各セルを構造化データにする**
  （`Regimen` 等に落とし込む。§4）。そうしないと薬剤詳細へのリンクが張れず、検索にも乗らない
- 本文を要約した結果として**判断が変わりうる情報が落ちる場合は、要約せず原文を残す**
  （例:「腎機能低下時は避ける」「妊婦には投与しない」等の禁忌・警告は、本文中にあっても必ず残す）
- 表が大きすぎて1画面に収まらない場合は、§2.5 のとおり**感染症の切り方を細かくして表を分割**する
  （表そのものを間引かない）
- 重症度スコア（A-DROP、CURB-65 等）は原典で表になっていれば**表として載せる**。
  ただし Phase 1 では**点数を自動計算する機能は作らない**（入力UIが増え、§2.5 の分量目安を超えるため）。
  自動計算は将来の別機能として切り出す

### 2.3 載せる（感染症1件につき、最大7項目）

| # | 項目 | 内容 | 備考 |
|---|---|---|---|
| 1 | 想定起炎菌 | 頻度順に3〜5菌まで | 菌名タップ →**既存の菌種別画面へ** |
| 2 | 経験的治療 | 第一選択／βラクタムアレルギー時 | 薬剤名タップ →**既存の薬剤詳細へ** |
| 3 | 標的治療 | 起炎菌判明後の de-escalation（記載がある感染症のみ） | 同上 |
| 4 | 投与期間 | 「5〜7日間」等の数値のみ | |
| 5 | 必須の検査 | 血液培養2セット等、**治療開始前に外せないものだけ** | |
| 6 | 当院固有の注意 | 入院／外来の別、使用申請の要否など | 該当があるときだけ表示 |
| 7 | 原典ページ | `source` として全レコードに必須 | 既存の `validate-data.mjs` で強制 |

### 2.4 載せない

- 疫学・病態生理・リスク因子の解説文
- 画像所見、鑑別診断のフローチャート
- 参考文献の羅列
- 既存の薬剤詳細画面に既にある情報（腎機能別用量、TDM目標値、AWaReバッジ、申請要否）
  → **二重管理になり、片方だけ古くなる事故が起きる。**必ず薬剤詳細側に一本化してリンクで送る

### 2.5 分量の目安

1感染症あたり **スマートフォン1〜2画面**（スクロール2回以内）を上限とする。
これを超えるものは、感染症の切り方が粗い（例:「肺炎」→「市中肺炎」「院内肺炎」に分ける）と判断する。

## 3. 画面構成

### 3.1 遷移

```
オープニング（大項目 4→5ボタン）
├─ 内服薬
├─ 注射薬
├─ 菌種別
├─ 感染症別   ← 新設
│   └─ 部位別カテゴリ（呼吸器／尿路／腹腔内／皮膚軟部組織／中枢神経／骨関節／血流・カテーテル／その他）
│        └─ 個別の感染症（例: 呼吸器 → 市中肺炎／誤嚥性肺炎／院内肺炎・VAP）
│             └─ 感染症詳細  ─(薬剤名タップ)→ 既存の薬剤詳細画面
│                            └(菌名タップ)  → 既存の菌種別画面
└─ その他
```

- 階層は既存レーンと同じ **3階層**（大項目 → 分類 → 個別）に揃える。深くしない
- ボタンの見た目・件数バッジは既存の `top-btn` / `top-grid` をそのまま使う（新規CSSは最小限）

### 3.2 入院／外来の出し分け（`tekisei_in` と `tekisei_out` の扱い）

**採用案：感染症詳細画面の中でタブ切替する。**

```
市中肺炎
 ┌──────────┬──────────┐
 │  外来     │   入院    │   ← ここで切り替え
 └──────────┴──────────┘
```

- **却下案**: オープニングで先に「入院／外来」を選ばせる
  → 既存の「成人／小児」の出し分けと二重になり、階層が1つ深くなる。
  同じ感染症の外来・入院を見比べたいという実際の使い方にも合わない
- 片方にしか記載がない感染症は、タブを出さず記載のある方だけを表示する

## 4. データモデル案

### 4.1 型定義（`src/types.ts` に追加）

```ts
/** 感染症の部位カテゴリ */
export type InfectionSite =
  | "respiratory" | "urinary" | "intraabdominal" | "skin_soft_tissue"
  | "cns" | "bone_joint" | "bloodstream" | "other";

/** 診療の場。原典 tekisei_in / tekisei_out に対応 */
export type CareSetting = "inpatient" | "outpatient";

/** 1つの推奨レジメン */
export type Regimen = {
  /** "first" = 第一選択 / "alternative" = βラクタムアレルギー時など */
  line: "first" | "alternative" | "targeted";
  /** 適用条件（"βラクタムアレルギー時" "緑膿菌リスクあり" 等）。null は無条件 */
  condition: string | null;
  /**
   * 使用する薬剤。**必ず既存の Drug.id で持つ**（文字列の薬剤名で持たない）。
   * これにより薬剤詳細への遷移が保証され、薬剤名の表記ゆれも起きない。
   * 併用は複数要素で表す（例: ["ceftriaxone", "azithromycin"]）
   */
  drugIds: string[];
  /** 原典どおりの用量表記。用量の正はあくまで薬剤詳細側 */
  text: string;
  /** 投与期間 */
  duration?: string;
  note?: string;
};

/**
 * 原典で表になっていた記載のうち、Regimen に収まらないものの受け皿。
 * 「表は構造を保ったまま残す」（§2.2）を満たすために持つ。
 * 例: 重症度分類、経口スイッチの基準、起炎菌別の第一選択の対応表
 */
export type InfectionTable = {
  caption: string;
  headers: string[];
  rows: string[][];
  note?: string;
  source: Source;
};

export type InfectionEntry = {
  id: string;
  name: string;
  /** 検索用の別名（"CAP" "市中肺炎" "はいえん" 等） */
  aliases: string[];
  site: InfectionSite;
  settings: CareSetting[];
  /** 想定起炎菌。既存の Organism.id で持つ */
  likelyOrganismIds: string[];
  /** setting ごとのレジメン */
  regimens: Partial<Record<CareSetting, Regimen[]>>;
  /** 治療開始前に外せない検査だけ */
  workup?: string[];
  /** 原典の表をそのまま残したもの（§2.2） */
  tables?: InfectionTable[];
  /** 本文から要約した、判断に効く注記（禁忌・警告は要約せず原文のまま） */
  keyPoints?: string[];
  /** 当院固有の注意 */
  facilityNote?: string;
  source: Source;
};
```

`tables` は既存のレイアウト検査（`scripts/check-layout.mjs`）が
「1列が表幅の70%以上を占める」「セルが1文字幅で折り返す」を機械的に弾くため、
**スマートフォン幅で破綻する表はビルド時に検出できる**。
検出された表は §2.2 の補足のとおり、感染症を分割して表を小さくする。

### 4.2 なぜ薬剤を ID で持つのか（本企画の肝）

ご要望の「**抗生剤治療についての記載が出てきたら薬剤別解説へ移動する**」は、
薬剤を `drugIds: ["ceftriaxone"]` の形で持てば自動的に満たされる。

- 表示名は `DRUG_BY_ID` から引くので、**薬剤名の表記ゆれが起きない**
- 存在しない薬剤IDを書いたら `validate-data.mjs` で**ビルドが落ちる**（リンク切れが起きない）
- 実装の前例がすでにある：アンチバイオグラムの抗菌薬略号タップ → 薬剤詳細
  （`src/components/OrganismDetail.tsx:114-122`、`DRUG_BY_ABBR` と `onOpenDrug`）
  同じ仕組みを `DRUG_BY_ID` で使うだけでよく、**新規の仕組みは不要**

### 4.3 既存データとの関係

- `src/data/diseases.json`（83件）は現在 **適応外使用の検索専用**。今回の感染症とは粒度が異なる
  （例: 「MRSA肺炎」は適応外使用の適応症名であり、経験的治療の単位ではない）
- したがって **新規に `src/data/infections.json` を作る**。`diseases.json` は変更しない
- 将来的に相互リンクの余地はあるが、Phase 1 では扱わない

## 6. 段階リリース

量が多い問題への現実的な対処として、**頻度順に区切って出す**。

- **Phase 1（骨組み＋5疾患）**: 市中肺炎／腎盂腎炎・膀胱炎／蜂窩織炎／腹腔内感染症／カテーテル関連血流感染
  - 画面と仕組みを先に完成させ、**書き方の型を確定する**
  - この5件をレビューしていただき、記載粒度の合意を取る
- **Phase 2 以降**: 合意した型に沿って残りを追加（データ追加のみ、コード変更なし）

Phase 1 のレビューを経ずに全件を書くと、**やり直しの量が最大になる**ため推奨しない。

## 7. 確認事項（実装前に回答が必要）

### 7-1. 【最重要】規程上の可否

現行の要件定義に次の定めがある。

> **NFR-012 法令**: 公開前にプログラム医療機器（SaMD）該当性を薬剤部・法務で確認する。
> **院内文書の閲覧支援に留め、診断・治療方針の提示は行わない**（`docs/02_要件定義書.md:333`）

「感染症別に経験的治療を提示する」機能は、この **「治療方針の提示は行わない」という線に触れる**。
また本アプリは GitHub Pages で**一般公開**されている（NFR-007、`https://teinekeijinkaier.github.io/Antibiotics/`）。

判断をお願いしたい点：

- (a) 本機能を「当院マニュアルの閲覧支援」の範囲内と整理してよいか。
  整理するなら、画面上は**アプリの推奨ではなく原典の引用**であることを明示する（下記 (c)）
- (b) 薬剤部・法務／感染対策委員会への確認は必要か
- (c) 表示上の但し書き案：
  「本項は{原典名}の記載を要約したものであり、**個々の患者の治療方針を示すものではない**。
  最終的な判断は主治医が行う。当院での用量・申請ルールは薬剤詳細画面を参照」

**この (a) の判断が出るまで、感染症の内容データの実装には着手しない。**
画面の骨組み（§5 の 1,3,4,5,7）は内容に依存しないため先行できる。

### 7-2. 原典の性質と著作権

- `tekisei_in` / `tekisei_out` は **当院作成の文書か、外部ガイドライン（学会・JAID/JSC等）の転載か**
- 外部ガイドラインの場合、**一般公開されるアプリへの転載可否**の確認が必要
  （`docs/02_要件定義書.md:378` に「原典PDFをアプリに同梱してよいか」が**未解決事項として残っている**）

### 7-3. 内容に関する確認

- 対象は **成人のみか、小児も含むか**（既存レーンは成人／小児を出し分けている）
- 感染症の分類は原典の章立てに従ってよいか、それとも §3.1 の部位別で切り直してよいか
- 用量の記載が原典と既存の薬剤データで食い違った場合、**どちらを正とするか**
  （案: 当院の薬剤詳細を正とし、感染症画面は選択薬と期間のみ示す）

### 7-4. 資料の受領

**`tekisei_in` / `tekisei_out` は本セッションに届いていない**（先の原典PDFのみ受領済み）。
このチャットにアップロードをお願いしたい。形式は PDF / Word / テキストいずれでも可。
